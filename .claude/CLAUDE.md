# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project: Action Wise

This repo is the backend for "Action Wise" (full product spec: `../.claude/handover.md`, cross-repo notes: `../.claude/CLAUDE.md`). The handover spec assumes a single pnpm monorepo (`apps/api`/`apps/web`/`packages/*`) — **that restructure was explicitly declined (2026-07-26); this stays a standalone repo through Phase 1.** Action Wise is a backend knowledge base/execution layer — Resources, Actions, Flows, Runs, Registry, Workspaces — being built out here section by section per the handover (A → G).

Stack already matches the target spec: Hono, Postgres+Drizzle, TypeScript strict, Zod. Architectural choices made along the way that weren't in the spec are logged in `../DECISIONS.md` — check it before assuming why a table/column is shaped the way it is. **Gaps vs. the spec to know about before extending:**
- No `packages/shared`, and there won't be one — Zod schemas are NOT shared with `frontent/`. Define request/response schemas here in `src/validations/`; when the frontend needs the matching shape, its schema is hand-written/synced separately, not imported. No compile-time guarantee they match — flag it when a schema changes shape.
- Auth is email/password only — handover also calls for GitHub OAuth (not implemented).
- `src/db/schema/` has the full Phase 1 domain model (`workspaces.ts`, `connections.ts`, `resources.ts`, `playground.ts`, `actions.ts`, `runs.ts`, `flow.ts` — barrel at `schema/index.ts`), migrated (`drizzle/0000_lazy_cable.sql`).
- **All Phase 1 backend sections (B–G) are built** (2026-07-30). Workspace CRUD/members/invites, `can()`, Connection/Resource CRUD, Playground boards/tiles/execution/promote, TS type export, fake data generation, Actions (CRUD + steps + sequential executor + `{{steps.*}}` resolver), and a workspace-level run-history endpoint all exist (see Architecture below).
- No Vitest — no test runner configured at all currently.
- **New required env var**: `CONNECTION_SECRET_KEY` (base64, must decode to exactly 32 bytes) — the app throws at import time without it, same eager-validation pattern as the other env vars. Generate one with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` and add it to your own `.env` (not committed, not read by any tooling here).

Where handover conventions and the global CLAUDE.md coding rules disagree, global wins for code-writing patterns (see `../.claude/CLAUDE.md` → Global conventions). Concretely here: implement the handover's "single `AppError` type, consistent JSON error envelope" as `{ message: string }`, matching the existing global response convention — don't invent a new envelope shape.

## State of repo

Hono backend built on `better-auth`, Drizzle (Postgres/Neon), and Redis, with the full Phase 1 domain surface (workspaces, connections, resources, playground, beautify/faker, actions, runs). Collection routes (list/create) mount under `/api/workspaces/:workspaceId/...`; item routes (get/update/delete by the item's own id) mount flat at their own top-level prefix (`/api/connections`, `/api/resources`, `/api/resource-folders`, `/api/playground`, `/api/actions`, `/api/invites`) — see the URL convention note in Architecture. **DB caveat (2026-07-30):** the Neon database behind `DATABASE_URL` is currently shared with a legacy app (finance/social tables) — see `../DECISIONS.md`. The legacy `connections` table collides with ours and must be renamed (`src/db/fix-collision.tmp.ts`) before the migration fully applies (`src/db/apply-migration.tmp.ts`); both `.tmp.ts` helpers are disposable once the user moves to a dedicated database.

## Commands

- `pnpm dev` — tsx watch src/index.ts (dev server, hot reload, port 3000)
- `pnpm build` — tsc compile to dist/
- `pnpm start` — node dist/index.js (run compiled build)
- `pnpm db:generate` / `pnpm db:push` — generate/apply migrations from `src/db/schema` (config in `drizzle.config.ts`, output to `./drizzle`)
- `pnpm db:seed` — runs `src/db/seed.ts`; seeds a full "Demo Workspace" (connections, folders, resources, runs, playground board/tiles, a 3-step action with a completed run) onto the user from `SEED_EMAIL` (falls back to first user). Idempotent-ish: skips if that user already has a "Demo Workspace"; delete it to re-seed.

No test runner or lint config. Manual API testing via `src/test/auth.http` (VS Code REST Client) — covers sign-up, sign-in, verify-email, forgot/reset password, change password, delete-user, sign-out.

## Architecture

**Auth is entirely delegated to `better-auth`.** `src/lib/auth.ts` constructs the `auth` instance and is the real center of the app:
- Drizzle adapter (`drizzleAdapter`) backs it with Postgres, schema from `src/db/schema/auth.ts` (users/sessions/accounts/verifications, `usePlural: true`).
- Redis (`src/lib/connect-redis.ts`) is wired in as `secondaryStorage` for get/set/delete — used for session/rate-limit state, not a general cache.
- Password hashing uses `@node-rs/argon2` via `hashPassword`/`verifyPassword` in `src/utils/password.ts`, passed into `emailAndPassword.password`.
- Email hooks (`sendResetPassword`, `sendVerificationEmail`, `sendDeleteAccountVerification`) come from `src/templates/emails/*` and are passed directly into the betterAuth config, not called manually.
- One custom `after` hook (`createAuthMiddleware`) with two branches: `/sign-up` (welcome email + personal workspace when a session exists) and `/sign-in` (`ensurePersonalWorkspace` backfill for users whose email-verification-gated signup couldn't create one — only fires at zero memberships). Both branches are try/catch-wrapped so a failure never fails the auth request.
- `connectRedis()` is awaited at module load time in `src/lib/auth.ts`; if it throws, the process exits(1) immediately. Redis must be reachable for the app to boot.

**Routing (`src/index.ts`)**: all routes are mounted on `basePath("/api")`. `/api/auth/*` is handled directly inline (`c => auth.handler(c.req.raw)`) — `requireAuth` middleware is registered globally with `app.use(requireAuth)` but placed *after* the auth routes, so it does not gate them; it applies to everything mounted below it. `requireAuth` (`src/middlewares/auth.ts`) calls `auth.api.getSession` and sets `userId` on context (typed via `AppEnv` in `src/types/hono.ts`).

**Domain schema (Phase 1, tables only — no routes yet)**: `src/db/schema/columns.helpers.ts` exports `idColumn`/`timestampColumns`/`createdByColumn` spreadable column groups (uuid v7 via `src/utils/id.ts`, `updated_at` auto-touched via `$onUpdate`) — every new domain table spreads these rather than redeclaring them. `src/db/schema/enums.ts` holds the `text` + CHECK-constraint role/status unions (`WORKSPACE_ROLES`, `INVITE_STATUSES`, `RUN_STATUSES`) — these are deliberately not `pgEnum`, see `../DECISIONS.md`. Closed sets not expected to grow (resource `kind`/`direction`/`danger`, connection `kind`, render mode, flow edge type/source) are native `pgEnum`.

**Error/validation conventions for new routes**: `src/utils/errors.ts` exports `AppError` (message + `ClientErrorStatusCode`), caught in `src/index.ts`'s `app.onError` and turned into `{ message }` JSON. `src/utils/validate.ts` exports `zv(target, schema)` — a `@hono/zod-validator` wrapper whose failure hook also returns `{ message }` at 400, so every new route's validation errors match the global response convention automatically.

**Layering convention (applies across all domains below)**: routes → controllers → services, but controllers *are* the Hono route handlers, not framework-agnostic wrappers. A route file just chains `method(path, [zv(...)], controllerFn)` — no inline arrow function extracting args and calling a controller. Each controller function takes `(c: Context<AppEnv>)` directly, reads `c.req.valid(target as never)` (the `as never` cast is a deliberate, accepted trade-off — Hono's `req.valid()` typing only resolves when the validator and handler are literally chained in the same route-registration expression, which a separately-defined named function can't satisfy), runs its own Drizzle queries, and returns `c.json(...)` itself. Business logic that's specific to one route lives directly in that controller function; small guard/assert helpers used only within one controller file are private (non-exported) functions in that same file. `services/` is reserved for: (a) third-party/external-I/O wrappers (`transporter.ts`, `invite-email.ts`, `crypto.ts`), and (b) functions that must stay standalone because they're called from more than one controller or from non-route code (e.g. `services/workspaces.ts`'s `createWorkspaceWithOwner`/`ensurePersonalWorkspace`, called from `src/lib/auth.ts`'s hooks; `services/resources.ts`'s `createResourceRow`, shared by `controllers/resources.ts` and `controllers/playground.ts`'s promote handler) — plus pure orchestration modules with no `Context` involvement that are substantial enough to warrant their own file even with a single caller (`execute-resource.ts`, `execute-action.ts`, `http-execute.ts`, `type-inference.ts`, `faker.ts`, `beautify.ts`).

**URL convention (applies across all domains below): `:workspaceId` only appears in the path where it's actually needed.** Every domain table's `id` (`uuid`, generated by `uuidv7()` — see `src/utils/id.ts`/`columns.helpers.ts`) is a standalone globally-unique PK, never composite with `workspaceId`, so an item lookup by id alone is safe. Each domain's `routes/<domain>.ts` exports two routers:
- A **collection router** (`xCollectionRouter`) for list/create — paths still start `/:workspaceId/...`, mounted under `app.route('/workspaces', ...)` in `src/index.ts`, still gated by `requireWorkspaceAccess(action)` middleware exactly as before.
- An **item router** (`xItemsRouter`) for get/update/delete/etc. by the item's own id — paths are flat (`/:connectionId`, `/:actionId/steps/:stepId`, ...), mounted directly at their own top-level prefix (`app.route('/connections', ...)`, `app.route('/actions', ...)`, etc. — NOT under `/workspaces`). These routes have no `requireWorkspaceAccess` middleware (there's no `:workspaceId` param for it to read) — instead the controller loads the row first, derives `workspaceId` from it (via a join to the parent row for the two tables with no direct `workspaceId` column: `playgroundTiles` → `board.workspaceId`, `actionSteps` → `action.workspaceId`), and calls `assertWorkspaceAccess(userId, workspaceId, action)` (`src/utils/permissions.ts`) itself — same DB round-trips, same 404-before-403 semantics, just relocated from middleware into the controller body.

Routes that keep `:workspaceId` even at the item level: the workspace resource itself (`GET/PATCH/DELETE /workspaces/:workspaceId`), and workspace members (`.../members/:userId` — a membership's natural key is `(workspaceId, userId)`, `userId` alone isn't unique across workspaces). Invite accept (token-only) and revoke (`inviteId` is a unique PK) both moved to a genuinely top-level `/invites` router, dropping `/workspaces` entirely.

**Workspaces (handover section B)**, `src/routes/workspaces.ts` exports `workspacesRouter` (mounted at `/api/workspaces` — workspace CRUD, members, invite collection, all genuinely workspaceId-scoped) and `inviteItemsRouter` (mounted at `/api/invites` — accept-by-token, revoke-by-`inviteId`) → both go through `src/controllers/workspaces.ts`: full CRUD, member list/role-change/remove, invites, all inlined directly in the controller. `src/services/workspaces.ts` is trimmed to just `createWorkspaceWithOwner`/`ensurePersonalWorkspace` (see layering convention above).

- `src/utils/permissions.ts` — `can(userId, action, subject)` (handover's literal ask), the lower-level `getWorkspaceRole`/`roleHasPermission` it's built from, and `assertWorkspaceAccess(userId, workspaceId, action)` (throws `AppError` 404/403 directly — the shared core used by both the middleware below and item-route controllers). `ROLE_PERMISSIONS` is the *only* place role→action mapping lives; extending for per-resource overrides later means editing this map, not call sites.
- `src/middlewares/workspace-access.ts` — `requireWorkspaceAccess(action)`, applied to collection routes only (the ones with `:workspaceId` in the path). Thin wrapper around `assertWorkspaceAccess` — reads `workspaceId` from `c.req.param`, never trusts it beyond using it as a lookup key. 404 for non-members, 403 for members with the wrong role — see `../DECISIONS.md` for why that split exists. Item routes don't use this middleware — see the URL convention note above.
- `src/services/invite-email.ts` — `InviteEmailSender` interface, `inviteEmailSender` is the console-logging stub instance per the handover's explicit ask. Swap the instance to add real sending later.
- Personal workspace on signup is wired into the *existing* `after` hook in `src/lib/auth.ts` (the one that already sends the welcome email) — `createWorkspaceWithOwner` when `ctx.context.newSession?.user` is present, plus the sign-in `ensurePersonalWorkspace` backfill branch (see Auth section above / `../DECISIONS.md` 2026-07-30). Don't add a second hook; extend that one. `listMembers` inner-joins `users` and returns `name`/`email` per member.
- `src/test/workspaces.http` — manual test file for all of the above, same REST Client pattern as `auth.http`.

**Connections & Registry (handover section C)**: `src/routes/connections.ts` exports `connectionsCollectionRouter` (`/api/workspaces/:workspaceId/connections`, list/create) and `connectionItemsRouter` (`/api/connections/:connectionId`, get/patch/delete/secret); `src/routes/resources.ts` exports `resourcesCollectionRouter` (`/api/workspaces/:workspaceId/resources` + `/resource-folders`, list/create), `resourceItemsRouter` (`/api/resources/:resourceId`, also folds in the Beautify/Faker handlers below), and `folderItemsRouter` (`/api/resource-folders/:folderId`) — all four route through `controllers/connections.ts`/`controllers/resources.ts`, same fat-controller layering as workspaces.

- `src/services/crypto.ts` — `encryptSecret`/`decryptSecret`, AES-256-GCM, key from `env.CONNECTION_SECRET_KEY`. `src/services/connections.ts`'s `getDecryptedConnectionSecret` is internal-only (Playground/Actions execution, sections D/G), the one function this domain keeps as a standalone service — nothing in C exposes a decrypted secret over the API; list/get responses only ever carry a `hasSecret: boolean` for the *requesting* user.
- Connection/resource permissions are separate `WorkspaceAction`s (`connection:read/write/delete`, `resource:read/write/delete`) in the same `ROLE_PERMISSIONS` map in `utils/permissions.ts` — `editor` can write but not delete; `viewer` is read-only. See `../DECISIONS.md` for why.
- `resources.connectionId`/`resources.folderId` (and `resource_folders.parentFolderId`) are cross-checked against the resource's own `workspaceId` via `assertConnectionInWorkspace`/`assertFolderInWorkspace`, kept exported in `services/resources.ts` alongside `createResourceRow` (the other resources function kept standalone — reused by `controllers/playground.ts`'s promote handler) — the DB FKs alone don't stop a resource from pointing at another workspace's connection.
- A resource's `kind` is immutable after creation (`updateResource` throws 400 on mismatch) since it determines the whole `config` shape — this is enforced inline in `controllers/resources.ts`, not the Zod schema, because Zod can't compare against the existing DB row.
- `src/test/connections.http`, `src/test/resources.http` — manual coverage, same pattern as the other `.http` files.

**Playground (handover section D, backend half only)**: `src/routes/playground.ts` exports `playgroundCollectionRouter` (`/api/workspaces/:workspaceId/playground/boards`, list/create boards) and `playgroundItemsRouter` (`/api/playground/boards/:boardId[/tiles]`, `/api/playground/tiles/:tileId[/execute|/runs|/promote]`) → `controllers/playground.ts`, no `services/playground.ts` — deleted in the layering refactor, everything inlined — boards, tiles, HTTP execute, Firebase run logging, promote-to-registry. The grid drag/resize UI and the per-tile ring buffer are frontend-only and don't exist here (ring buffer is never persisted at all — see `../DECISIONS.md`).

- Gating differs from C: board/tile CRUD and execute only require `workspace:read` (any member, including `viewer`) since Playground is a personal scratchpad, not shared content — see `../DECISIONS.md`. Only `POST .../tiles/:tileId/promote` requires `resource:write`, because that's the one endpoint that writes a real `resources` row.
- `src/services/http-execute.ts` — the actual HTTP client: `{{variable}}` templating (`resolveTemplate`/`resolveTemplateDeep`), auth header construction from a connection's `auth` type + the user's decrypted secret (`buildAuthHeaders`), header redaction before persisting (`redactHeaders`), and the `fetch` wrapper with a 30s timeout (`executeHttpRequest`). Pure functions — no DB access — kept as a standalone service module (see layering convention above).
- `HttpConnectionConfig` (`db/schema/connections.ts`) grew an `auth` field in this section (`none`/`bearer`/`apiKey`/`basic`) — it didn't exist when Connections shipped in C because nothing needed to actually *use* a connection yet. See `../DECISIONS.md` if a Connection created before this looks like it's missing the field (jsonb, no migration was needed, but existing rows written via the old shape won't have `auth` and execution will fail against them).
- A tile is either `resourceId`-backed (points at a saved Resource) or `adhocConfig`-backed (its own inline kind/address/config, not yet saved) — never both, enforced by a Zod `.refine` in `validations/playground.ts`. `POST .../promote` is what turns the latter into the former, via the same `createResourceRow` service from section C.
- Only `kind: "http"` tiles can hit `POST .../execute` (proxied server-side per the handover). Firebase tiles execute client-side and get recorded via `POST .../tiles/:tileId/runs` instead, carrying whatever `request`/`response`/`status` the frontend already has.
- `src/test/playground.http` — manual coverage, same pattern as the other `.http` files.

**Beautify & Faker (handover E/F)**, two extra endpoints folded into `resourceItemsRouter` in `src/routes/resources.ts` rather than a new router: `GET /api/resources/:resourceId/export-type` and `POST .../fake-data` (both `resource:read`, checked in-controller via `assertWorkspaceAccess` after loading the resource). Both are pure/ephemeral — nothing is persisted, every call re-derives from the resource's recorded `runs`.

- `src/services/type-inference.ts` — `inferTypeFromSamples`/`renderTypeScript`. Deliberately flatter than a full quicktype engine (a field is assumed consistently primitive/object/array across samples, not a mixed shape) — see `../DECISIONS.md`. `isEnumLike` is the important bit: a string field only becomes a literal union if some value *repeats* across samples, not just because the distinct count is small — with few Runs, everything looks like a small closed set otherwise (this was a real bug, caught and fixed by hand-testing before trusting it).
- `src/services/faker.ts` — `generateFakeRecords`, built on **`@ngneat/falso`** (per explicit instruction, not a default choice). Field-name regex heuristics (email/id·uuid/name/phone/url/price·amount/`_at`·date/status/description) pick a generator; an `isEnumLike` field's real observed values always win over a name guess; genuinely unmatched strings fall back to `randNoun()` — never a bare `"string"` placeholder, per the handover's explicit "a type-only generator... is a failure."
- `src/services/beautify.ts` orchestrates both: pulls successful `runs.response` rows for a resource (unwrapping `.body` for `http`, using the raw value for firebase kinds — see the comment there for why), runs it through inference, then either renders TS or hands the shape to `faker.ts`. Throws 400 if the resource has zero successful runs yet — there's nothing to infer from.

**Actions (handover section G)**: `src/routes/actions.ts` exports `actionsCollectionRouter` (`/api/workspaces/:workspaceId/actions`, list/create) and `actionItemsRouter` (`/api/actions/:actionId[/steps[/:stepId]|/execute|/runs[/:actionRunId]]`) → `controllers/actions.ts`, Zod in `validations/actions.ts`, manual coverage in `src/test/actions.http`. No `services/actions.ts` — Actions/Steps CRUD is inlined directly in the controller (with private helpers `requireAction`/`listSteps`/`requireStep`/`assertHttpResourceInWorkspace`/`assertStepNameAvailable`/`getRunDetail`; `requireAction(actionId, userId, action)` loads by id alone and calls `assertWorkspaceAccess` itself — no `:workspaceId` in these routes). The one thing kept as a standalone service is the executor:

- Action CRUD + nested step CRUD (`POST/PATCH/DELETE .../steps[/:stepId]`, order auto-appended `max+1`, compacted on delete) + `PUT .../steps/reorder` (registered *before* `/:stepId` routes so "reorder" never matches as an id). Step names are `^[A-Za-z0-9_]+$` and unique per action — they're the `{{steps.<name>}}` reference keys.
- `POST .../execute`: the controller validates the action has steps, then hands off to `services/execute-action.ts`'s `runActionSteps` — kept as its own service module (not inlined) even with a single caller, because it's a stateful DB-writing orchestration loop with no `Context` involvement, same rationale as `execute-resource.ts`. It runs steps sequentially: per step, `input_mapping` values are resolved against prior steps' in-memory results (private `resolveStepRef` in that file — refs live **only** in input_mapping, resolved values become plain flat variables for the resource's own `{{var}}` templates), then executed through the shared `executeHttpResourceRun` (`services/execute-resource.ts`, extracted from the old `executeTile` — Playground's controller uses the same function). Per-step `runs` rows carry `step_id`/`action_run_id`; first failure (fetch error, HTTP ≥ 400, or unresolved ref) stops the chain and finishes the `action_runs` row as "error". The controller then re-reads the finished run via its local `getRunDetail` and returns HTTP 200 with the run detail even on failure — the timeline consumes partials. See `../DECISIONS.md` (2026-07-30 entries) for the resolver/permission/reorder rationale.
- Firebase-kind resources are rejected as steps at create/update time (only `http` executes server-side).
- Run reads: `GET /api/actions/:id/runs[?limit]` and `GET /api/actions/:id/runs/:actionRunId` (timeline payload) — both item routes, no workspaceId — plus workspace-level `GET /api/workspaces/:workspaceId/runs?limit&resourceId` (`src/routes/runs.ts`, `resource:read`, unchanged collection query) for dashboard/recent-history.
- Permissions: `action:read/write/delete/execute` in `ROLE_PERMISSIONS` — editor gets execute, viewer does not (writes shared runs; see DECISIONS.md).

**Env validation** (`src/utils/env.ts`): all required vars (`DATABASE_URL`, `REDIS_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `EMAIL_ID`, `EMAIL_PASS`, `PORT`, `CONNECTION_SECRET_KEY`) are asserted eagerly via `requiredEnv()` — missing any one throws at import time, before the server starts. `SEED_EMAIL` is deliberately NOT in env.ts (seed-only, read directly off `process.env`).

**Email sending** (`src/services/transporter.ts`): nodemailer configured for Gmail service using `EMAIL_ID`/`EMAIL_PASS`. All templates share one HTML shell (`src/templates/emails/template.ts`) and are exported through `src/templates/emails/index.ts`.
